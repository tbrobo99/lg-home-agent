# The app shell

The UI is a single-page app with no framework, no bundler and no `node_modules` in
the repository. It is three files served straight from `app/web/`:

```
app/web/
├── index.html              markup + an inline SVG icon sprite
├── style.css               the whole visual system (~560 lines)
├── app.js                  state, rendering, event delegation (~560 lines)
├── manifest.webmanifest    name, icons, standalone display
├── sw.js                   service worker (shell cached, /api never cached)
├── icon-192.png            generated by tools/icon-source.html
└── icon-512.png            same, at 512 px
```

Everything the page needs is fetched from `/api/*`, so the same files work whether
they are served by `run.py`, a static host, or a WebView.

## Screens

| Screen | What is on it |
|---|---|
| Devices | Room tabs, a temperature / humidity / running summary, the two-column device grid, quick actions, and the next scheduled task |
| Schedule | Every task with its repeat rule and next run, plus per-task delete |
| Assistant | The decision-mode switch, the conversation, suggestion chips, and the composer |

The Assistant tab opens with a **Cascade / Agent** switch. It is not a setting for
the app — it is a setting for *how the sentence gets answered*, and it applies to
everything, including the quick actions and the chips:

- **Cascade** — code picks the layer from the shape of the sentence. ~1 ms for
  anything the rules know.
- **Agent** — the rules' reading is shown to the model as a suggestion and the
  model keeps it or plans its own. Every reply then carries a collapsed line under
  the bubble — *"declined the reading · 2 steps"* — which opens to the actual steps,
  including the reading that was turned down.

The switch posts to `/api/mode` and takes effect on the next message; `config.json`
sets which one the app starts in.

Tapping a device card opens a bottom sheet with the target temperature, the mode
pills and a power button. Tapping the power button on the card itself toggles the
device without opening the sheet.

The quick actions are real commands, not shortcuts: they post a sentence to
`/api/chat`, so they go through the same parser as typed input. "Cool 24°C" sends
`turn on the living room AC and set it to 24 degrees`, and the room tab changes
which room the sentence names.

## Install it on a phone

The page is a valid PWA, so it installs to the home screen with no store, no APK
and no build step.

1. Start the server so the phone can reach it:

   ```bash
   python run.py --lan
   ```

   It prints something like `Phone: http://192.168.1.23:8848`. The laptop and the
   phone must be on the same network.

2. Open that URL on the phone.

   - **Android / Chrome** — menu → *Add to Home screen* → *Install*.
   - **iOS / Safari** — share → *Add to Home Screen*.

3. Launch it from the home screen. It opens full screen, without browser chrome,
   and remembers the shell offline.

There is no authentication. Anyone who can reach the port can control the
appliances, so only run `--lan` on a network you trust.

## Packaging as an Android APK

Capacitor wraps the same files in a WebView. This is optional — the PWA already
installs to the home screen — but it gives you a real APK to hand in, and it lets
the app talk to a fixed address without typing a URL.

The native project is already generated and committed under `android/`
(Capacitor 8, Gradle 8.14, `com.example.homeagent`). `node_modules/` is not.

```bash
npm install                 # Capacitor CLI + runtime
npx cap sync android        # copies app/web into the native project
npx cap open android        # opens Android Studio: Run, or Build > Build APK
```

Or from the command line, with an Android SDK installed and `ANDROID_HOME` set:

```bash
cd android && ./gradlew assembleDebug
# android/app/build/outputs/apk/debug/app-debug.apk
```

### Point it at your agent

`capacitor.config.json` decides where the WebView loads from:

```json
{
  "appId": "com.example.homeagent",
  "appName": "Home Agent",
  "webDir": "app/web",
  "server": {
    "url": "http://192.168.1.1:8848",
    "cleartext": true
  }
}
```

Change that `url` to the machine running the agent — the router itself if you run
it there — then `npx cap sync android` again. `server.url` makes the app a thin
client, so the phone always sees live state and the scheduler keeps running when
the phone is asleep. If you would rather ship the shell inside the APK, drop
`server.url` and store the host in `localStorage` with a settings field instead.

The host is plain HTTP, so the manifest already carries
`android:usesCleartextTraffic="true"`; without it Android 9+ silently blocks every
request.

**Not verified here:** the APK build itself. This machine has no Android SDK, so
the steps above were generated and synced but never compiled. The `android/`
project is stock Capacitor — the only hand edits are the cleartext flag, the app
name, and the icons.

## Icons and splash screens

`tools/make_icons.py` renders every icon from the HTML sources next to it, using
any Chromium-based browser in headless mode:

```bash
python tools/make_icons.py
```

It writes the two PWA icons, the five launcher densities (legacy, round and
adaptive foreground), and the ten splash screens. Set `BROWSER=/path/to/chrome`
if the lookup misses yours. Note that `--window-size` does not size the viewport
in current headless builds, so the script pins the document to the target box
instead of trusting it.

## Why no framework

The whole UI is a render function over one snapshot object, refreshed every four
seconds. At this size a framework would add a build step, a lockfile and a
dependency tree to a project whose selling point is that it runs on a router with
`python3` and nothing else.
